# Provenance-faithful agent traces and context engineering for model handoff

## How should agent traces be modeled and stored faithfully and cheaply (OTel GenAI, PROV, trace models, event sourcing, file-impact capture)?

### Takeaway
OpenTelemetry's GenAI conventions (still "Development" status, now in a separate `semantic-conventions-genai` repo) give a usable vocabulary for agent/tool spans: `execute_tool {gen_ai.tool.name}` spans, with the provider-supplied `gen_ai.tool.call.id` only when one exists, and **opt-in** argument and result capture that is flagged as sensitive. W3C PROV (Entity/Activity/Agent with used/wasGeneratedBy/wasAssociatedWith) is the standard provenance graph, and PROV-AGENT applies it to AI agents. For file impact, vendors snapshot cheaply but only partially. Claude Code checkpoints only edits made through its own editing tools and states that it is not a replacement for git.

### Cited Findings
**OpenTelemetry GenAI semantic conventions**
- The GenAI conventions have moved out of the main semconv site. The opentelemetry.io page now says "Important GenAI semantic conventions have moved to the OpenTelemetry GenAI semantic conventions repository", and old registry attributes such as `gen_ai.tool.call.arguments`, `gen_ai.tool.call.id` and `gen_ai.tool.call.result` are marked "Deprecated – Moved" — [opentelemetry.io agent-spans page](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-agent-spans/); [OTel registry gen-ai](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)
- In the new repo, agent/tool attributes have stability "Development". `gen_ai.tool.name` is Required on the tool/command execution span. `gen_ai.tool.call.id` is "Conditionally Required… If and only if the model or provider supplied a tool call identifier". `gen_ai.tool.type` (function/extension/datastore) is Recommended. **`gen_ai.tool.call.arguments` and `gen_ai.tool.call.result` are `Opt-In`** and carry the warning "This attribute may contain sensitive information" — [semantic-conventions-genai: gen-ai-agent-spans.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- Arguments: "When the attribute is recorded on events, it MUST be recorded in structured form. When recorded on spans, it MAY be recorded as a JSON string if structured format is not supported", and "Instrumentations MUST follow [JSON schema]" — [same](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- Conversation id: when no identifier is available, "instrumentations SHOULD NOT populate conversation id. For example, a new UUID, a trace identifier, or a hash of request content SHOULD NOT be used as a fallback value." Sensitive URI components "SHOULD be scrubbed" — [same](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- The new spec also defines skill spans ("Load skill span", "Read skill resource span", "Command execution span") with `gen_ai.skill.name` and `gen_ai.skill.resource.name` — [same](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)
- Version history (secondary source, Greptime, May 2026): v1.38 added tool definitions/call details and `invoke_agent` guidance. v1.39 added **MCP semantic conventions**. v1.40 added retrieval spans and cache token attributes. v1.41 made `execute_tool` span names include the tool name, added `invoke_workflow`, and split `invoke_agent` into CLIENT/INTERNAL. Its MCP example shows `gen_ai.operation.name = execute_tool`, `mcp.method.name = tools/call`, `mcp.session.id`, `jsonrpc.request.id`, and `network.transport = pipe` for stdio — [Greptime blog](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)
- Metrics include `gen_ai.invoke_agent.tool_calls` and `gen_ai.execute_tool.duration`. "An agent run is a trace, a tool call is a span, a model call is a span" — [Dash0](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained) (secondary)

**W3C PROV**
- PROV-O, a W3C Recommendation since 30 Apr 2013, defines Entity, Activity and Agent, linked by `wasGeneratedBy`, `used`, `wasAssociatedWith`, `wasAttributedTo`, `wasDerivedFrom` and `wasInformedBy` — [W3C PROV-O](https://www.w3.org/TR/prov-o/); [CASRAI summary](https://casrai.org/dictionary/term/prov-o)
- Definitions: "Generation is the completion of production of a new entity by an activity." `wasInformedBy` means "activity a2 is dependent on or informed by another activity a1, by way of some unspecified entity that is generated by a1 and used by a2" — [W3C PROV-O](https://www.w3.org/TR/prov-o/)
- PROV-AGENT (ORNL, arXiv 2508.02866) models agent interactions with standard PROV relations ("used, wasGeneratedBy, wasAssociatedWith, and wasInformedBy"), so that "the resulting graph is fully connected and queryable" — [PROV-AGENT](https://arxiv.org/html/2508.02866v1)

**File-impact capture**
- Claude Code: "checkpointing automatically captures the state of your code before each prompt you send that starts a turn". It keeps "file snapshots for the 100 most recent checkpoints in a session". Snapshots are deleted in a retention sweep "by default about 30 days" after the session last saved one. Discarding a checkpoint "deletes the snapshot files that no remaining checkpoint references", which implies shared, deduplicated snapshot storage — [Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing)
- Claude Code limitations: "Checkpointing does not track files modified by Bash commands" (rm/mv/cp). It does not track external changes or edits from concurrent sessions. Subagent edits are usually not restored. Symlinked and hard-linked paths are skipped. Checkpoints are "Not a replacement for version control" — [Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing)
- Gemini CLI: "When you approve a tool that modifies the file system (like `write_file` or `replace`), the CLI automatically creates a 'checkpoint.'" — [Gemini CLI checkpointing](https://geminicli.com/docs/cli/checkpointing/)

### Inferences
- For Continuum, the OTel shape maps onto the existing gateway: one `execute_tool` record per dispatched action. However, OTel `gen_ai.tool.call.id` is explicitly the *provider's* id, and that matches AGENTS.md invariant 4: store it for correlation, never use it as operation identity. Keep `(run_id, operation_key)` as the identity.
- OTel makes argument/result capture opt-in because of sensitivity. A cheap, faithful design stores structured arguments in the event (needed for identity binding), but puts large or sensitive results in a separate content-addressed blob table referenced by hash. That gives deduplication and lets retention or erasure act on blobs without mutating immutable events. This is the "claim-check" idea, which I could not verify from a primary source this session (see Gaps).
- PROV gives a clean vocabulary for handoff packets. An artifact (Entity) `wasGeneratedBy` an action (Activity) `wasAssociatedWith` a model or runtime (Agent). That lets a packet separate runtime-verified facts from model claims (invariant 8).
- Vendor checkpointing misses shell-driven changes, so a reliable file-impact record needs a before/after workspace content hash (for example a git tree hash) around *every* side-effecting call, not only around editor-tool calls.

## What do vendors and practitioners recommend for building a bounded, high-signal context for a new model?

### Takeaway
Everyone converges on the same approach. Treat context as a scarce "attention budget". Externalize durable state into structured files or stores (progress logs, JSON feature lists, todo/NOTES files, memory directories). Make compression *restorable* by keeping identifiers and paths, not contents. Clear stale tool results first. Pass distilled summaries between agents, or full traces when decisions are implicit. Anthropic's long-running harness pairs this with git and end-to-end verification, because models otherwise declare victory early.

### Cited Findings
**Anthropic: "Effective context engineering for AI agents" (29 Sep 2025)**
- Context is a "finite resource with diminishing marginal returns". LLMs have an "attention budget", and context rot means recall drops as tokens increase — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Goal: "finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome" — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Just-in-time retrieval: agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools" — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Compaction in Claude Code: "The model preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs or messages… plus the five most recently accessed files." "One of the safest lightest touch forms of compaction is tool result clearing" — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Structured note-taking: "the agent regularly writes notes persisted to memory outside of the context window", for example a to-do list or NOTES.md. Claude playing Pokémon kept tallies "across thousands of game steps" — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Sub-agents: each "might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)" — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**Anthropic: "Effective harnesses for long-running agents" (26 Nov 2025)**
- An initializer agent sets up "an `init.sh` script, a claude-progress.txt file that keeps a log of what agents have done, and an initial git commit", plus "a structured JSON file with a list of end-to-end feature descriptions" — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Why JSON: "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files". Agents may edit only "the status of a passes field". Prompt text: "It is unacceptable to remove or edit tests" — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Bearings routine for each new session: run `pwd`; "Read the git logs and progress files"; "Read the features list file and choose the highest-priority feature that's not yet done" — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Failure modes: agents tried "to one-shot the app… leaving the next session to start with a feature half-implemented and undocumented". A later instance "would look around, see that progress had been made, and declare the job done" — [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Anthropic platform: context editing, memory tool, compaction**
- `clear_tool_uses_20250919` (beta header `context-management-2025-06-27`) clears the oldest tool results past a `trigger` (default 100,000 input tokens). It keeps `keep` recent pairs (default 3) and supports `clear_at_least`, `exclude_tools`, and `clear_tool_inputs` (default false). Cleared results are replaced with placeholder text. "Clearing invalidates cached prompt prefixes". `clear_thinking_20251015` handles thinking blocks. The "client keeps the full, unmodified history". Server-side compaction is called "the primary strategy for most long-running conversations" — [Claude docs: context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- With the memory tool enabled, "Claude gets an automatic warning to save important information to its memory files before the tool results are cleared" — [Claude docs: context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- The memory tool (`memory_20250818`) "operates client-side". The `/memories` prefix maps onto the application's storage. Commands are view/create/str_replace/insert/delete/rename. The auto-injected system prompt includes "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" and "ASSUME INTERRUPTION: Your context window might be reset at any moment" — [Claude docs: memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The memory tool's multi-session pattern has an initializer session, a progress log plus a feature checklist, an end-of-session update, and the rule "Mark a feature complete only after end-to-end verification confirms it works, not when the code is written." The docs also say "compaction keeps the active context small… and memory preserves the information that must survive summarization" — [Claude docs: memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Security guidance: strip sensitive data before writes, cap file sizes, "Periodically delete memory files that haven't been accessed in a long time", and validate every path against traversal (including URL-encoded `%2e%2e%2f`) — [Claude docs: memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

**OpenAI: Responses API compaction**
- Purpose: compaction is used "to reduce context size while preserving state needed for subsequent turns". It runs server-side via `context_management` with `compact_threshold`, or through a standalone `/responses/compact` endpoint. The compaction item "is opaque and not intended to be human-interpretable". The docs say "do not prune `/responses/compact` output… pass it into your next `/responses` call as-is". It is ZDR-friendly with `store=false` — [OpenAI compaction guide](https://developers.openai.com/api/docs/guides/compaction)

**Google ADK**
- ADK separates "`Session` / `State`: It's your short-term memory during one specific chat" from "Long-Term Knowledge (`MemoryService`): It's a searchable archive or knowledge library… potentially containing information from many past chats" — [ADK Memory docs](https://google.github.io/adk-docs/sessions/memory/) (now served at adk.dev)

**Manus: "Context Engineering for AI Agents" (Yichao "Peak" Ji, 18 Jul 2025)**
- "KV-cache hit rate is the single most important metric for a production-stage AI agent." Cached Claude Sonnet input costs 0.30 USD/MTok vs 3 USD/MTok uncached, "a 10x difference" — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- "Keep your prompt prefix stable" (no second-precise timestamps). "Make your context append-only." "Ensure your serialization is deterministic" (stable JSON key order) — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Mask tool logits rather than removing tools. Treat "the file system as the ultimate context". "Our compression strategies are always designed to be restorable… web page can be dropped… as long as the URL is preserved" — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
- Recitation: rewriting todo.md is "reciting its objectives into the end of the context". "leave the wrong turns in the context". "don't few-shot yourself into a rut" — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

**Cognition: "Don't Build Multi-Agents" (Walden Yan, 12 Jun 2025)**
- Principles: "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions". In the Flappy Bird example, subagents misread their subtasks and produced a Super Mario background and an inconsistent bird. Recommendation: "use a single-threaded linear agent". For long tasks, add an LLM "whose key purpose is to compress a history of actions & conversation into key details, events, and decisions" — [Cognition](https://cognition.ai/blog/dont-build-multi-agents)

### Inferences
- There is a tension between Anthropic (distilled summaries of 1–2k tokens between agents) and Cognition (share full traces, because actions carry implicit decisions). A reconciliation that fits Continuum: the packet carries a *distilled, verified* state, plus explicit decision records extracted from actions, plus restorable identifiers (event IDs, blob hashes, file paths) for just-in-time drill-down into the full trace.
- The Anthropic harness findings (JSON over Markdown, edit only a `passes` field, verify end-to-end before marking done, agents declaring victory early) are direct empirical support for Continuum's runtime-owned milestones and verifier-gated progress (invariants 1 and 7).
- Manus's KV-cache guidance argues for a deterministic, stable-ordered packet serialization with a fixed prefix (policy and schema first, volatile state last). It also argues for keeping failed actions or errors in the packet rather than scrubbing them.
- OpenAI's compaction item is opaque and provider-bound. It cannot serve as a cross-vendor handoff medium, so a model-agnostic handoff must build its own human-auditable packet. This is consistent with invariant 9 (no silent degradation).

## Why have big vendors not solved cross-session memory (failure modes, poisoning, privacy, cost)?

### Takeaway
Persistent memory turns every untrusted input into a potential *persistent* instruction. Rehberger's SpAIware showed that ChatGPT memory could be written by indirect prompt injection and used for exfiltration across all future chats; OpenAI fixed the exfiltration channel, but not memory writes. MINJA showed that query-only users can poison a shared agent memory. Implicit "reference chat history" memory also degrades user control over context, a problem practitioners call a "dossier". Vendors therefore fall back to user-reviewable, deletable, application-controlled memory rather than an autonomous global store.

### Cited Findings
- SpAIware (Johann Rehberger, 20 Sep 2024): through "prompt injection from untrusted data (such as analyzing an untrusted document or navigating to an untrusted website)", attackers can invoke the memory tool "to insert fake long-term memories or malicious instructions". Thereafter "all new conversation going forward will contain the attacker's instructions and continuously send all chat conversation messages and replies to the attacker" — [Embrace The Red](https://embracethered.com/blog/posts/2024/chatgpt-macos-app-persistent-data-exfiltration/)
- OpenAI mitigated the exfiltration channel (`url_safe` checks; macOS app fix in Sep 2024), but "memory injection is not fixed: a website or untrusted document can still invoke the memory tool to store arbitrary memories". Rehberger advises users to review memories regularly, delete them, or use temporary chats — [Embrace The Red](https://embracethered.com/blog/posts/2024/chatgpt-macos-app-persistent-data-exfiltration/). Reports differ on how complete the fix was: The Hacker News says "patched" ([THN](https://thehackernews.com/2024/09/chatgpt-macos-flaw-couldve-enabled-long.html)), TechRadar says "partial fix" ([TechRadar](https://www.techradar.com/pro/hacker-creates-false-memories-in-chatgpt-to-steal-victim-data-but-it-might-not-be-as-bad-as-it-sounds)). Reporting also says OpenAI initially classed the report as a "model safety" issue rather than a security vulnerability.
- MINJA (arXiv 2503.03704, Mar 2025; later retitled "Memory Injection Attacks on LLM Agents via Query-Only Interaction"): attackers inject malicious records "by only interacting with the agent via queries and output observations". They use bridging steps plus "progressive shortening" so that poisoned records are retrieved for a *different* victim user's query. The authors call for memory isolation, authentication and secure memory management — [arXiv 2503.03704](https://arxiv.org/abs/2503.03704)
- A follow-up (arXiv 2601.05504, Jan 2026) cites >95% injection success and ~70% attack success "under idealized conditions" for such attacks. It notes that robustness in realistic deployments and effective defenses "remain understudied", and evaluates the attacks on EHR agents — [arXiv 2601.05504](https://arxiv.org/html/2601.05504v1)
- User-control failure: after ChatGPT's April 2025 "reference chat history" upgrade, Simon Willison saw an unrequested "HALF MOON BAY" sign in an image, added "because you've mentioned being in Half Moon Bay before". His argument: "The entire game when it comes to prompting LLMs is to carefully control their context". The previous memory was browsable and deletable, but "The new memory feature removes that control completely… It's effectively collecting a dossier" (21 May 2025) — [Simon Willison](https://simonwillison.net/2025/May/21/chatgpt-new-memory/)
- Anthropic puts memory safety on the integrator: "Your application executes every file operation Claude requests, so these safeguards are your responsibility". This covers sensitive-data stripping, size caps, expiration and path-traversal checks — [Claude docs: memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Cost pressure: cached vs uncached input differs by 10x (Manus figure). Context editing "invalidates cached prompt prefixes", so memory and context mutation have a direct cost — [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus); [Claude docs: context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Context rot means that adding more remembered material can lower recall accuracy — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### Inferences
- The root problem is provenance. Vendor memories are written by the model from mixed trusted and untrusted inputs, without recording who or what caused the write, so poisoned and genuine memories look the same. A runtime that records the source of every memory item (user utterance vs tool output vs model inference, with event IDs) can down-rank or quarantine claims derived from untrusted tool output. This matches Continuum's invariant 8: unverified model claims are not facts.
- Relevance and staleness are a second unsolved axis. Willison's example is irrelevant recall, not malicious recall. Scoping memory to repo, task or run, and showing the user exactly what was injected, addresses it better than global, implicit memory.
- Privacy and erasure conflict with append-only logs. Content-addressed blobs that can be deleted, referenced from immutable events, are the standard reconciliation (inference; no primary source fetched).

- I did not collect quantitative data on memory-feature costs or on user opt-out rates.
